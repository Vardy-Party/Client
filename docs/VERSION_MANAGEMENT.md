# VardyParty Version Management Automation

This document describes the automated version management system for VardyParty applications (MAUI and Linux/Avalonia).

## Overview

The version management system provides:
- **Centralized version control**: Single source of truth in `Version.props`
- **Auto-incrementing ApplicationVersion**: Increments on every GitHub Actions build
- **Semantic versioning for ApplicationDisplayVersion**: Bumped on main branch merges
- **DLL stamping**: Assemblies are tagged with version information
- **Git tagging**: Automatic release tags created on version bumps
- **Integration with CI/CD pipelines**: Works seamlessly with existing ci.yml, cd.yml, and release.yml

## Version Scheme

### ApplicationVersion (Internal Build Counter)
- Integer value that increments with every build
- Used internally by the system
- Reset or managed manually via GitHub Actions
- **Current: 35**

### ApplicationDisplayVersion (Semantic Version)
- User-facing version in format `Major.Minor.Patch`
- Incremented on main branch merges (default: minor bump)
- Displayed to end users
- **Current: 1.7.2**

### Assembly Versioning
- Auto-generated by MSBuild from Version.props
- `AssemblyVersion`: Follows ApplicationDisplayVersion (e.g., `1.7.2.0`)
- `AssemblyFileVersion`: Equals ApplicationVersion (internal build counter)
- `AssemblyInformationalVersion`: Combines both (e.g., `1.7.2+35`)
- Automatically stamped into DLLs at compile time

## Files Modified/Created

### Central Configuration
- **`Version.props`** (NEW)
  - Single source of truth for all version numbers
  - Imported by both `VardyParty.csproj` and `VardyParty.Linux.csproj`
  - Format:
    ```xml
    <ApplicationVersion>35</ApplicationVersion>
    <ApplicationDisplayVersion>1.7.2</ApplicationDisplayVersion>
    <AssemblyVersion>$(ApplicationDisplayVersion).0</AssemblyVersion>
    <AssemblyFileVersion>$(ApplicationVersion)</AssemblyFileVersion>
    <AssemblyInformationalVersion>$(ApplicationDisplayVersion)+$(ApplicationVersion)</AssemblyInformationalVersion>
    ```

### Project Files
- **`VardyParty/VardyParty.csproj`** (MODIFIED)
  - Added: `<Import Project="..\Version.props" />`
  - Removed: Duplicate `<ApplicationVersion>` and `<ApplicationDisplayVersion>` properties

- **`VardyParty.Linux/VardyParty.Linux.csproj`** (MODIFIED)
  - Added: `<Import Project="..\Version.props" />`
  - Removed: Duplicate `<ApplicationVersion>` and `<ApplicationDisplayVersion>` properties

### Assembly Info Files
- **`VardyParty/GlobalAssemblyInfo.cs`** (NEW)
  - Sets assembly-level metadata (Company, Product, Copyright, etc.)
  - Attributes automatically filled by MSBuild from Version.props

- **`VardyParty.Linux/GlobalAssemblyInfo.cs`** (NEW)
  - Same as above for Linux app

### GitHub Actions Workflows
- **`.github/workflows/auto-increment-build-version.yml`** (NEW)
  - Automatically increments `ApplicationVersion` after each build
  - Can be called as a reusable workflow
  - Outputs new version numbers

- **`.github/workflows/bump-display-version.yml`** (NEW)
  - Bumps `ApplicationDisplayVersion` on main branch merges
  - Supports major, minor, or patch version bumps
  - Creates annotated git tags for releases
  - Can be triggered manually via `workflow_dispatch`

- **`.github/workflows/build.yml`** (NEW)
  - Primary build workflow
  - Runs on: push to main/develop/feature branches, pull requests
  - Calls `auto-increment-build-version.yml` when pushing to main
  - Displays final version information

## Usage

### Automatic Version Incrementing

**On Every Build (GitHub Actions):**
1. Push code to any branch or merge to main
2. GitHub Actions runs the build workflow
3. `ApplicationVersion` is automatically incremented
4. Changes are committed back to the branch

**ApplicationVersion Flow:**
- Feature branch push: Incremented ✓
- Main branch push: Incremented ✓
- PR created: NOT incremented (no commits)

### Manual Version Bump

**To bump ApplicationDisplayVersion manually:**

Option 1: Use GitHub UI
1. Go to Actions > Bump Display Version on Main Merge
2. Click "Run workflow"
3. Select version bump type (major, minor, or patch)
4. Workflow updates Version.props, commits, pushes, and creates tag

Option 2: Manual edit
1. Edit `Version.props` locally
2. Change `<ApplicationDisplayVersion>` to new version
3. Commit and push to main
4. GitHub Actions will create a git tag

### When Packaging/Building Releases

**Do NOT manually edit Version.props for normal development.** The system handles it automatically.

If you need to manually bump the display version:
1. Trigger the `bump-display-version` workflow manually
2. Or make a direct commit to `Version.props` with your new version
3. Ensure format is `Major.Minor.Patch`

## Updated CI/CD Configuration

### Update cd.yml - Windows Package Step

Replace the version extraction in `package-windows` job:

```yaml
- name: Extract app version metadata
  id: app_version
  run: |
    # Read from Version.props instead of .csproj
    [xml]$versionProps = Get-Content "Version.props"
    $displayNode = $versionProps.SelectSingleNode('//ApplicationDisplayVersion')
    $buildNode = $versionProps.SelectSingleNode('//ApplicationVersion')
    $display = if ($null -ne $displayNode) { $displayNode.InnerText } else { "" }
    $build = if ($null -ne $buildNode) { $buildNode.InnerText } else { "" }
    
    if ([string]::IsNullOrWhiteSpace($display) -or [string]::IsNullOrWhiteSpace($build)) {
      Write-Host "ERROR: ApplicationDisplayVersion/ApplicationVersion missing in Version.props"
      exit 1
    }
    "APP_DISPLAY_VERSION=$display" | Out-File -FilePath $env:GITHUB_ENV -Append
    "APP_BUILD_VERSION=$build" | Out-File -FilePath $env:GITHUB_ENV -Append
    "display=$display" | Out-File -FilePath $env:GITHUB_OUTPUT -Append
    "build=$build" | Out-File -FilePath $env:GITHUB_OUTPUT -Append
    Write-Host "Using app version: $display (build $build)"
  shell: powershell
```

### Update cd.yml - Android Package Step

Replace the version extraction in `package-android` job:

```bash
- name: Extract app version metadata
  id: app_version
  run: |
    # Read from Version.props

```

### DLL Stamping Verification in CI

To verify DLLs are stamped correctly, add this step to ci.yml after build:

```yaml
- name: Verify DLL version stamping
  run: |
    # Find any DLL and check its version attributes
    DLL=$(find . -name "VardyParty*.dll" -type f | head -1)
    if [ -f "$DLL" ]; then
      echo "Found DLL: $DLL"
      dotnet tool install -g dotnet-version-extensions || true
      dotnet asm "$DLL" | grep -E "Version|FileVersion|InformationalVersion" || echo "Version info embedded in assembly"
    fi
  shell: bash
  continue-on-error: true
```

## FAQ

**Q: Will this break my existing CI/CD?**
A: No. Version.props is imported by the projects at build time. The CI workflow reads versions the same way. You can update cd.yml to read from Version.props when ready.

**Q: Do I need to update ci.yml?**
A: No. ci.yml doesn't read versions—it just builds. MSBuild automatically uses Version.props via the project Import statement.

**Q: What about release.yml?**
A: release.yml is tag-triggered. For automatic version bumping, the new `bump-display-version` workflow creates the tags that trigger release.yml.

**Q: Can I still manually edit Version.props?**
A: Yes, but don't do it during normal development. Let the automation handle increments. Manual edits should go through a PR first.

**Q: How do I know if DLL stamping is working?**
A: Inspect the DLL properties in File Explorer (Windows) or use `dotnet asm` tool to check AssemblyVersion attributes.
